1

LLM이란 정확히 무엇인가

"인공지능이 자연스럽게 말한다"는 직관 이전에, LLM은 "다음 토큰을 확률로 예측하는 함수"일 뿐입니다. 이 한 문장에 모든 게 들어있습니다.

1-1. LLM의 한 줄 정의

CORE DEFINITION

LLM = "지금까지의 텍스트를 보고, 다음에 올 단어(토큰)의 확률을 출력하는 함수"

입력: "삼성디스플레이의 OLED 증착은" (지금까지의 토큰 sequence)
출력: 다음 토큰의 확률 분포 — "공정의 30%, 핵심의 25%, 매우의 8%, 노벨의 0.001%, ..."
이 함수를 수십억~수조 개 매개변수parameter, 가중치 · weight로 만들어낸 것이 바로 LLM입니다.

ChatGPT, Claude, Gemini가 "대화를 한다"고 느끼지만, 내부에서 일어나는 일은 단순합니다 — "지금까지의 대화를 보고 다음 한 토큰을 예측"하는 동작을 수천 번 반복합니다. "삼성디스플레이의 OLED 증착은 [공정]" → 다시 "...[공정] [의]" → 다시 "...[의] [핵심]" → ... 한 토큰씩 자기회귀(autoregressive)로 생성합니다.

1-2. 토큰(Token)이란? — 모든 것의 시작

TERM · 토큰 (Token)

"LLM이 처리하는 텍스트의 최소 단위"

토큰은 "단어"가 아닙니다. 단어보다 작거나 클 수 있습니다. 영어는 보통 한 단어가 1~3개 토큰, 한국어는 한 글자가 1~3개 토큰으로 쪼개집니다. 토크나이저(tokenizer)는 BPEByte Pair Encoding, 가장 자주 등장하는 byte 쌍을 합쳐가는 방식 또는 SentencePiece 같은 알고리즘으로 학습됩니다.

실제 토큰화 예시 — GPT-4 토크나이저 기준

입력 문장: "Samsung Display는 OLED 증착 공정에서 세계 1위입니다."

토큰 분할:

Samsung Display 는 OLED 증 착 공 정 에서 세계 1 위 입니다 .

각 토큰의 ID (어휘집의 번호):

28920 8113 16969 14248 94731 28944 31619 25193 38573 61521 220 26953 59159 13

※ 실제 토큰 ID는 모델·버전마다 다릅니다. 위는 GPT-4 토크나이저 패턴 기반 예시입니다. "Samsung"·"Display" 같은 자주 쓰이는 영어는 한 토큰, "증착" · "공정" 같은 한국어는 글자 단위로 쪼개집니다 — 한국어가 영어보다 토큰을 더 많이 쓰는 이유입니다.

왜 이게 중요한가: LLM API 비용은 "토큰당 가격"으로 매겨집니다. 같은 의미의 문장이라도 한국어는 영어보다 토큰을 1.5~3배 많이 쓰므로 비용도 그만큼 늘어납니다. 사내 LLM 운영 시 토큰 효율은 직접적인 비용 요인입니다.

1-3. 토큰 → 벡터 → 다음 토큰 예측 — 전체 흐름

1-4. 모델 매개변수(Parameter) 크기 — 왜 GPT-4가 GPT-2보다 똑똑한가

"매개변수 ~B(billion)"이라는 표현을 자주 보지만 실제로 어떤 의미인지 정리합니다. 매개변수는 학습된 가중치 숫자의 총 개수입니다. 7B 모델은 70억 개 숫자를 갖고 있다는 뜻이고, 각 숫자가 4 byte라면 모델 파일 크기는 약 28GB입니다. 가중치가 많을수록 더 미세한 패턴을 학습할 수 있지만 학습·추론 비용도 그만큼 큽니다.

GPT-21.5B~3 GB2019년 · 한 노트북에서도 추론 가능
GPT-3175B~350 GB2020년 · A100 GPU 8장 필요
Llama 3.1 8B8B~16 GB오픈소스 · 한 GPU에 탑재

중요한 직관: 매개변수가 많다고 항상 좋은 것은 아닙니다. 사내 도메인 작업(예: 사내 SOP 검색 + 답변)에서는 8B~70B 모델이면 충분한 경우가 많고, RAG로 외부 지식을 주입하면 작은 모델이 큰 모델을 능가하는 경우가 흔합니다. "큰 모델 = 좋다"는 단순한 등식은 깨진 지 오래입니다.
2

벡터(임베딩) 완전 이해 — 단어가 숫자가 되는 법

"벡터화"는 RAG의 핵심 메커니즘이자 LLM 내부의 핵심입니다. 도표와 숫자 예시로 끝까지 따라가 봅니다.

2-1. 왜 벡터(숫자)로 바꿔야 하나

WHY · 컴퓨터는 "글자"를 모른다

컴퓨터는 "비슷한 의미"를 비교할 수 없다 — 숫자로 바꿔야만 가능

컴퓨터에게 "사과"와 "배"는 그냥 다른 글자입니다. 둘 다 과일이라는 사실, "테이블"보다 "포도"에 가깝다는 사실을 컴퓨터가 알기 위해서는 각 단어를 의미를 반영한 숫자(벡터)로 바꿔야 합니다. 그러면 "사과 벡터"와 "배 벡터" 사이의 거리가 작고, "사과 벡터"와 "테이블 벡터" 사이의 거리가 크다고 계산할 수 있습니다. 이것이 모든 의미 검색 · RAG · LLM의 출발점입니다.

2-2. 벡터(임베딩)란? — 한 줄 정의

TERM · 임베딩 (Embedding)

"단어 · 문장 · 문서를 N차원 공간의 한 점(숫자 배열)으로 표현한 것"

예) "OLED 증착" → [0.21, -0.85, 0.43, 0.12, ..., -0.07] (1024차원 벡터)
의미가 비슷한 두 텍스트는 벡터 공간에서 가깝게 위치하도록 학습됩니다. 벡터의 차원 수는 보통 384, 768, 1024, 1536, 3072 중 하나로 모델마다 다릅니다.

2-3. 2차원으로 직관 이해 — 단어들의 지도

실제 임베딩은 수백~수천 차원이지만 사람은 시각화할 수 없습니다. 2차원으로 줄여서 보면 단어들의 "의미 지도"가 만들어집니다. 비슷한 의미의 단어가 모여 있고, 카테고리 사이가 떨어져 있는 모습이 보입니다.

위 그림은 직관적 시각화입니다. 실제로는:

  • "디스플레이"와 "반도체"는 가까운 거리 (산업적으로 연관) → 의미 거리 작음
  • "디스플레이"와 "강아지"는 먼 거리 (전혀 다른 영역) → 의미 거리 큼
  • "OLED"와 "QLED"는 매우 가까움 (같은 디스플레이 종류) → 의미 거리 매우 작음
  • "증착"과 "OLED"는 가까움 (OLED 만드는 핵심 공정) → 산업 컨텍스트 반영

2-4. 의미 거리는 어떻게 계산하나 — 코사인 유사도

TERM · 코사인 유사도 (Cosine Similarity)

"두 벡터가 가리키는 방향이 얼마나 비슷한가" — −1 ~ +1 사이의 값

두 벡터 A, B의 코사인 유사도 = (A·B) / (|A| × |B|)
(·는 내적, |·|는 크기) · 1에 가까우면 같은 방향(매우 비슷), 0이면 무관, −1이면 정반대. 텍스트 임베딩에서는 보통 0.7~1.0 범위가 "유사", 0.3 이하가 "무관"으로 해석됩니다.

실제 숫자로 따라가기 — 4차원 단순화 예시

WORKED EXAMPLE (4D 단순화)

"OLED" vs "QLED" vs "강아지" 코사인 유사도 계산

[가상의 4차원 임베딩 벡터] OLED = [ 0.8, 0.6, 0.1, -0.2] QLED = [ 0.7, 0.7, 0.1, -0.1] 강아지 = [ 0.1, -0.2, 0.9, 0.5] [OLED ↔ QLED 유사도] 내적: 0.8×0.7 + 0.6×0.7 + 0.1×0.1 + (-0.2)×(-0.1) = 0.56 + 0.42 + 0.01 + 0.02 = 1.01 크기 |OLED| = √(0.64+0.36+0.01+0.04) = √1.05 ≈ 1.025 크기 |QLED| = √(0.49+0.49+0.01+0.01) = √1.00 = 1.000 유사도 = 1.01 / (1.025 × 1.000) ≈ 0.985 ← 매우 비슷! [OLED ↔ 강아지 유사도] 내적: 0.8×0.1 + 0.6×(-0.2) + 0.1×0.9 + (-0.2)×0.5 = 0.08 - 0.12 + 0.09 - 0.10 = -0.05 크기 |강아지| = √(0.01+0.04+0.81+0.25) = √1.11 ≈ 1.054 유사도 = -0.05 / (1.025 × 1.054) ≈ -0.046 ← 거의 무관! [해석] • OLED ↔ QLED: 0.985 → 거의 같은 방향 (의미 매우 유사) • OLED ↔ 강아지: -0.046 → 무관 (다른 카테고리) → 검색 시: "OLED" 질문에 대해 QLED 문서는 가져오고 강아지 문서는 가져오지 않음. 이것이 의미 검색의 원리.

2-5. 임베딩 차원 — 384, 768, 1024, 3072의 의미

임베딩 모델이 출력하는 벡터의 차원 수는 모델마다 다릅니다. 일반적으로 차원이 클수록 더 미세한 의미를 표현하지만 비용도 커집니다. 어느 정도가 적절한지는 작업의 성격과 인프라 제약에 달려 있습니다.

임베딩 모델차원한 벡터 저장 크기 (float32)특징
all-MiniLM-L6-v23841.5 KB빠르고 작음 · 한국어 약함
all-mpnet-base-v27683.0 KB다용도 · 영어 우수
multilingual-e5-base7683.0 KB다국어 (한국어 포함)
BGE-M310244.0 KB다국어 · 긴 문맥 지원
OpenAI text-embedding-3-small15366.0 KBAPI · 비용 효율적
OpenAI text-embedding-3-large307212.0 KBAPI · 가장 정확
저장 비용 직관: 차원 1024짜리 임베딩으로 사내 문서 100만 chunk를 저장하면 4 GB입니다. 차원 3072짜리로 같은 작업을 하면 12 GB입니다. 검색 속도도 차원에 비례해 느려집니다. 따라서 무조건 큰 차원이 좋은 게 아니라 "정확도와 비용의 trade-off"를 고려해 선택합니다.

2-6. 임베딩 모델은 어떻게 학습되나

임베딩 모델은 LLM과 다른 구조로 학습됩니다. 가장 흔한 방법은 "대조 학습(Contrastive Learning)"입니다 — "비슷한 문장 쌍은 가깝게, 다른 문장 쌍은 멀게" 만들도록 학습합니다. 구체적으로 (질문, 정답 문장) 쌍을 수천만~수억 개 모아서 학습합니다 (예: 자연어 추론 데이터셋, 검색 로그, Wikipedia 페어 등).

INDUSTRY · 사내 운영 시 임베딩 선택 가이드

한국어 사내 문서 RAG라면

  • 다국어 지원: BGE-M3, multilingual-e5, OpenAI text-embedding-3 권장 (한국어 처리 우수)
  • 차원: 768~1024가 정확도/비용 균형점. 3072는 정밀 검색이 필요할 때만
  • 온프레미스 vs API: 보안 민감하면 BGE-M3 같은 오픈소스를 자사 GPU에서 돌림. 비용 우선이면 OpenAI API
  • 도메인 특화: 일반 임베딩이 부족하면 사내 문서로 fine-tuning (몇 만 쌍이면 충분)
3

RAG는 왜 필요한가 — LLM의 3가지 한계

RAG는 "LLM에 외부 지식을 붙이는 가장 실용적인 방법"입니다. 그런데 왜 그게 필요한가? 한계 3가지부터 시작합니다.

3-1. LLM의 한계 ① — 환각 (Hallucination)

환각이란: LLM이 그럴듯하게 들리지만 사실이 아닌 내용을 생성하는 현상. "Samsung Display의 OLED 증착 라인은 평택 P3에 있다"라고 자신있게 답하지만 실제로는 천안 · 아산에 있는 식. LLM은 "다음 토큰을 확률로 예측"하므로 진실 여부와 무관하게 가장 그럴듯한 단어를 선택합니다.

환각은 LLM이 학습한 패턴 중 가장 확률이 높은 것을 출력하기 때문에 발생합니다. "진실"을 따로 학습하는 것이 아니라 "사람이 자주 말하는 패턴"을 학습하기 때문입니다. 특히 사내 정보 · 최신 정보 · 특수 도메인에서 환각이 자주 발생합니다.

3-2. LLM의 한계 ② — 지식 컷오프 (Knowledge Cutoff)

LLM은 특정 시점까지의 데이터로만 학습됩니다. 그 시점 이후의 사건 · 새 제품 · 새 SOP는 알지 못합니다. 예를 들어 "2026년 4월에 발표된 Samsung Display의 신제품"을 묻는다면 LLM은 모릅니다.

모델학습 컷오프 (대략)이후 지식
GPT-4 (원본)2021년 9월알 수 없음
GPT-4 Turbo2023년 4월알 수 없음
GPT-4o2023년 10월알 수 없음
Claude 3.5 Sonnet2024년 4월알 수 없음
Llama 3.12023년 12월알 수 없음

3-3. LLM의 한계 ③ — 사내 데이터 미인지

LLM은 공개된 인터넷 텍스트로 학습되었으므로 사내 SOP · 8D 보고서 · 프로젝트 자료를 알지 못합니다. "ECN-2024-1129번 변경 이력을 알려줘"라고 물으면 LLM은 그 문서를 본 적이 없으므로 답할 수 없습니다. 만약 답한다면 그것은 100% 환각입니다.

3-4. RAG의 한 줄 정의 — 이 3가지를 동시에 해결

RAG · 한 줄 정의

"질문할 때 관련 문서를 찾아서 LLM에게 함께 보여주고 답하게 하는 방법"

① 환각 방지 — LLM이 "지어내는" 대신 "주어진 문서를 인용"
② 최신 지식 — 문서를 추가만 하면 즉시 반영 (LLM 재학습 불필요)
③ 사내 데이터 — 사내 EDM의 SOP · ECN · 보고서 등을 LLM이 즉시 활용

3-5. RAG의 단순한 아이디어를 그림으로

3-6. RAG vs 다른 대안 비교

방법원리장점단점
전체 학습 (Pre-training) 사내 데이터를 포함해 LLM을 처음부터 학습 모든 답변이 자연스러움 수십억 원 비용 · 수개월 · 거의 비현실적
Fine-tuning 기존 LLM에 사내 데이터로 추가 학습 도메인 어조 · 스타일 학습 새 정보 반영에 재학습 필요 · 환각 문제 잔존
Long Context 긴 문맥(100만 토큰 등)에 모든 문서를 통째로 넣음 구현 단순 · 검색 불필요 매 질문마다 비용 폭증 · 100만 토큰도 한계
RAG 질문할 때마다 관련 문서만 검색해 LLM에 전달 즉시 갱신 · 비용 효율 · 환각 감소 · 인용 가능 검색 품질에 의존 · 인덱스 관리 필요
실무 결론: 사내 코파일럿의 95% 이상은 RAG로 만들어집니다. Fine-tuning은 답변 어조 · 형식을 맞추는 데 보조적으로, Long Context는 한 회의록을 통째로 분석하는 등 특수한 경우에만 씁니다. RAG가 사내 LLM의 표준 아키텍처라고 보시면 됩니다.
4

RAG 7단계 파이프라인 — 문서 → 답변까지

RAG 시스템을 만들 때 거치는 7단계를 도표 · 그림과 함께 자세히 따라갑니다. 이 7단계가 RAG의 모든 것입니다.

4-1. 전체 파이프라인 한눈에

4-2. Step 1 — 문서 수집 (Ingestion)

모든 RAG의 출발점입니다. EDM · SharePoint · 사내 wiki 등에서 문서를 가져와 표준 형식(주로 PDF 또는 텍스트)으로 변환합니다.

  • 입력 형식 다양성: PPT, Excel, Word, PDF, HTML, 이미지(스캔된 SOP) 등
  • 변환 도구: Apache Tika · Unstructured.io · LlamaParse · Azure Document Intelligence 등
  • 이미지 텍스트 처리: OCR (Tesseract, AWS Textract) — 스캔된 SOP나 손글씨가 있을 때
  • 표 처리: 표 구조 보존이 매우 중요 (특히 사양·KPI 표). 단순 텍스트 변환은 표를 망가뜨림
  • 메타데이터 보존: 작성자 · 부서 · 작성일 · 권한 등급 · 프로젝트 ID 등을 함께 저장

4-3. Step 2 — Chunk 분할

WHY · chunk가 필요한 이유

"문서 전체를 통째로 임베딩하면 검색 정확도가 떨어진다"

100페이지 SOP를 하나의 벡터로 만들면 모든 내용이 평균화되어 "이 문서는 SOP다"라는 정도의 정보만 남습니다. 반면 200~500 토큰 단위 chunk로 쪼개면 각 chunk가 독립적인 의미 단위가 되어 정확한 검색이 가능합니다. "SOP 안의 step 5 절차"를 묻는 질문이 정확한 chunk를 찾아낼 수 있는 것입니다.

Chunk 분할 전략 — 4가지

전략방법장점단점
고정 크기 매 500 토큰씩 자름 (overlap 50) 구현 단순 · 균일 의미 경계 무시 · 문장 중간 절단
문장 기반 문장 단위로 묶어 chunk 만듦 의미 단위 보존 chunk 크기 들쭉날쭉
구조 기반 제목 · 섹션 단위로 자름 문서 구조 보존 구조가 명확한 문서에만 유효
시맨틱 청킹 문장 임베딩 거리로 의미 단위 자동 감지 의미 일관성 최고 처리 비용 큼
INDUSTRY · 사내 RAG 권장 chunk 설정

한국어 사내 문서 기준

  • chunk 크기: 300~500 토큰 (한국어 약 150~250자)
  • overlap: 50 토큰 (앞 chunk와 겹쳐 의미 끊김 방지)
  • 분할 기준: 문장(. ?! 등) 또는 단락(\n\n) 경계 우선
  • 예외: 표는 통째로 한 chunk로 처리 (split하면 표 망가짐)

4-4. Step 3 — 임베딩 변환

Section 2에서 자세히 다룬 부분입니다. 각 chunk를 임베딩 모델에 통과시켜 1024차원 벡터로 변환합니다. 이 단계가 RAG의 "지능"을 결정합니다 — 임베딩이 의미를 잘 반영해야 검색이 정확해집니다.

4-5. Step 4 — 벡터 DB 저장

임베딩 벡터를 빠르게 검색할 수 있는 자료구조에 저장합니다. 단순 list가 아닌 ANNApproximate Nearest Neighbor, 근사 최근접 이웃 인덱스(HNSW · IVF 등)를 사용해 100만 벡터에서도 50ms 이내에 검색이 가능합니다.

4-6. Step 5 — 검색 (Retrieval)

사용자 질문을 같은 임베딩 모델로 벡터화한 뒤, 벡터 DB에서 코사인 유사도가 가장 높은 K개 chunk를 가져옵니다 (보통 K=3~10).

4-7. Step 6 — 증강 (Augmentation) · 프롬프트 조립

검색된 chunk들을 LLM이 이해할 수 있는 형태로 프롬프트에 끼워넣습니다. 흔한 형식:

PROMPT TEMPLATE 예시

실전 RAG 프롬프트 구조

[시스템 메시지] 당신은 Samsung Display 사내 자료를 참고해 답변하는 어시스턴트입니다. 주어진 문서를 근거로만 답하고, 모르면 "자료에 없습니다"라고 답하세요. 모든 답변에 출처(문서명 · 페이지)를 표시하세요. [검색된 문서들] [문서 1] ECN-2024-1129.pdf, p.3 "...이번 변경의 주된 사유는 식각 균일도 개선이며, 기존 ±5% 변동을 ±2% 이내로 관리하기 위함이다..." [문서 2] SOP-Etch-v3.2.pdf, p.7 "...신규 spacer etch 레시피는 2024.12.15부터 적용..." [문서 3] 2024-12-Etch-월간보고.pdf, p.12 "...ECN-1129 적용 후 12월 균일도 ±1.8%로 개선..." [사용자 질문] ECN-2024-1129번의 변경 사유는 무엇인가요? [LLM의 답변] ECN-2024-1129번의 변경 사유는 식각 균일도 개선입니다. 기존 ±5% 변동을 ±2% 이내로 관리하기 위해 spacer etch 레시피가 2024.12.15부터 변경되었습니다. 📄 출처: • ECN-2024-1129.pdf, p.3 • SOP-Etch-v3.2.pdf, p.7

4-8. Step 7 — 생성 (Generation)

LLM이 위 프롬프트를 받아 답변을 생성합니다. 이때 LLM은 주어진 문서를 근거로 답하도록 시스템 메시지로 강제되어 환각이 크게 줄어듭니다. 답변 끝에 출처를 함께 표시하면 사용자가 직접 원본 문서를 확인할 수 있어 신뢰가 높아집니다.

핵심: 7단계 중 사용자가 직접 보는 것은 마지막 1개(답변)뿐이지만, 답변 품질을 결정하는 것은 앞의 6단계입니다. RAG 시스템 운영의 90%는 "검색이 잘 되는가"에 집중하고, LLM 자체는 거의 건드리지 않습니다.
5

실제 예시 따라가기 — 사내 EDM 질문 한 건이 답변이 되기까지

앞서 배운 7단계가 실제로 어떻게 돌아가는지, 가상의 사내 시나리오로 끝까지 따라갑니다.

5-1. 시나리오 — 신입 엔지니어의 질문

상황: Samsung Display의 한 신입 엔지니어가 사내 LLM 챗봇에 물어봅니다.
질문: "OLED 증착 공정에서 도가니 교체 직후 두께가 자주 spec 벗어나는데 일반적으로 어떻게 처리하나요?"
기대: 사내에 축적된 SOP · 8D · 보고서를 종합한 정확한 답변

5-2. 사전 작업 — 인덱싱은 이미 완료된 상태 (1주일 전)

이미 사내 EDM의 모든 문서(가정: 50만 건)가 chunk로 쪼개져 벡터 DB에 저장되어 있습니다. 신입 엔지니어가 질문하는 시점에는 검색만 하면 되는 상태입니다.

사전 작업 (1주일 전 완료)

사내 EDM 인덱싱 통계 (가상)

[수집] EDM 문서 총 50만 건 (PPT 30%, Word 25%, Excel 20%, PDF 25%) → PDF로 통일 변환 [Chunk 분할] 평균 문서당 12 chunk (페이지 단위 기준) → 총 600만 chunk [임베딩] BGE-M3 (다국어, 1024 dim) → 600만 × 1024 dim × 4 byte = ~24 GB 벡터 데이터 처리 시간: GPU 8장 × 6시간 = 48 GPU·hour [벡터 DB 저장] FAISS HNSW 인덱스 + 메타데이터(부서·권한·날짜) → 검색 latency 50ms 이내 보장 [갱신 정책] 매일 야간: 신규/변경 문서만 incremental 추가 (수만 건) 매월 1일: 전체 인덱스 재구축 (drift 방지)

5-3. 질의 시점 — 7단계가 실시간으로 진행됨

실시간 진행 (T+0 ~ T+3초)

질문이 답변이 되는 전체 과정

━━ T+0초: 사용자 질문 입력 ━━ "OLED 증착 공정에서 도가니 교체 직후 두께가 자주 spec 벗어나는데 일반적으로 어떻게 처리하나요?" ━━ T+0.05초: Step 5 (검색) ━━ 1) 질문을 BGE-M3로 임베딩 → q = [0.31, -0.42, 0.18, ..., 0.27] (1024 dim) 2) 권한 필터: 사용자 부서가 접근 가능한 chunk만 후보 → 600만 chunk 중 380만 chunk가 후보 3) FAISS HNSW로 top-20 검색 결과: ① SOP-OLED-Evap-v4.1.pdf, p.18 (0.892) — 도가니 교체 SOP ② 8D-2024-#127.pdf, p.5 (0.871) — 두께 spec 이탈 사례 ③ ECN-2023-0814.pdf, p.2 (0.856) — 도가니 워밍업 변경 ④ Etch-Quarterly-2024Q3.pdf, p.31 (0.834) — Q3 도가니 분석 ⑤ ... (총 20개) ━━ T+0.20초: Re-ranking (선택적) ━━ Cross-encoder로 top-20을 다시 정렬 → top-5만 남김 ① ① ② ③ → 그대로 유지 ④ → ⑤로 강등 (다른 도가니 사례가 더 우선) ━━ T+0.30초: Step 6 (증강) — 프롬프트 조립 ━━ [시스템] "주어진 문서로만 답하고 출처를 표시하세요" [문서 1] SOP-OLED-Evap-v4.1.pdf, p.18 "도가니 교체 후 첫 24시간은 워밍업 기간이며, 이때 두께 변동이 ±15% 수준까지 확대될 수 있다. 표준 절차는..." [문서 2] 8D-2024-#127.pdf, p.5 "2024년 5월 도가니 교체 후 첫 lot에서 두께 spec 초과 12% 발생. 원인 분석 결과 워밍업 시간 부족..." [문서 3] ECN-2023-0814.pdf, p.2 "기존 12시간 워밍업을 24시간으로 변경..." [문서 4] ... [문서 5] ... 5-4. 무엇이 잘 작동했는가

INDUSTRY · 이 시나리오에서 RAG의 가치

3가지 한계가 모두 해결됨

  • ① 환각 방지: LLM이 자기 학습 데이터로 답하지 않고, 사내 SOP·8D·ECN을 직접 인용
  • ② 최신 정보: 2024년 5월 8D 사례(LLM 학습 시점 이후)도 답변에 즉시 반영
  • ③ 사내 데이터: 인터넷에 없는 사내 ECN-2023-0814가 답변의 핵심 근거가 됨
  • + 권한 제어: 사용자 부서가 접근 불가능한 문서는 검색 후보에서 제외
  • + 출처 추적: 사용자가 답변 근거를 직접 확인 가능 → 신뢰도 ↑

5-5. 만약 검색이 실패한다면

RAG의 가장 큰 실패 모드: 검색이 정확한 chunk를 못 가져오면 LLM은 부정확한 문서로 답하거나 "자료에 없습니다"를 반환합니다. 예: 질문에 "도가니 교체"라는 정확한 표현이 없고 "crucible swap"이라고 영어로 적었다면 한국어 chunk가 안 잡힐 수 있습니다. 이 경우 다국어 임베딩 + 동의어 사전 + Hybrid 검색(Section 7)으로 보완합니다.

이것이 RAG 운영의 핵심 작업이 "LLM 모델 선택"이 아니라 "검색 품질 끌어올리기"인 이유입니다. 검색이 정확한 문서를 가져오면 어떤 LLM이든 좋은 답을 만듭니다. 반대로 검색이 잘못되면 어떤 LLM도 좋은 답을 만들 수 없습니다.

6

벡터 DB 비교 — FAISS · Pinecone · Weaviate · Chroma · pgvector

RAG의 심장인 벡터 DB 5가지를 비교합니다. 사내 환경 · 보안 요구 · 규모에 따라 선택이 달라집니다.

6-1. 벡터 DB가 하는 일 — 한 줄 요약

TERM · 벡터 DB (Vector Database)

"수백만~수십억 개 벡터 중 질의 벡터에 가장 가까운 K개를 매우 빠르게 찾는 시스템"

단순 list로 코사인 유사도를 모두 계산하면 100만 벡터 검색에 10초 걸립니다. 벡터 DB는 HNSW · IVF · ScaNN 같은 ANN 인덱스로 50ms 이내에 같은 검색을 끝냅니다. 검색 정확도는 약간 희생하지만 (97~99% 수준) 속도가 200배 빨라집니다.

6-2. 5대 벡터 DB 비교표

DB유형강점약점적합한 상황
FAISS 라이브러리 (Meta) 빠름 · 무료 · 가장 많은 인덱스 옵션 DB 아님 (운영 도구 직접 만들어야) 연구·프로토타이핑 · 자체 운영
Pinecone SaaS (managed) 운영 zero · 자동 스케일 비용 · 외부 서비스 의존 (보안) 빠른 시장 출시 · 보안 민감 X

7

고급 RAG 기법 — 단순 RAG의 한계를 넘는 5가지

기본 RAG로 시작했다면 곧 한계를 느낍니다. 사내 운영에서 자주 쓰이는 고급 기법 5가지를 정리합니다.

7-1. Hybrid Search — 키워드 + 시맨틱 검색 결합

WHY · 시맨틱 검색만으로는 부족한 경우

"ECN-2024-1129" 같은 정확한 ID는 키워드 검색이 더 강하다

시맨틱(임베딩) 검색은 의미적 유사도에 강하지만, "ECN-2024-1129" 같은 정확한 식별자나 부품 번호 검색은 약합니다. 반면 BM25Best Matching 25 — 1990년대 개발된 키워드 기반 점수화 알고리즘. 문서의 단어 빈도와 희귀도(IDF)를 가중 평균하여 검색 점수를 계산. 구글·검색 엔진의 전통적 표준 같은 전통 키워드 검색은 정확한 토큰 일치에 강합니다. 이 둘을 결합한 것이 Hybrid Search입니다.

방법강한 케이스약한 케이스
시맨틱 (Vector) "식각 후 두께가 안 맞는다" → "Etch CD 변동" 문서 "ECN-2024-1129" 정확한 ID
키워드 (BM25) "ECN-2024-1129", "model XR-203B" 정확한 식별자 표현 다른데 의미 같은 문서
Hybrid (둘 다) 두 가지 모두 강함 구현 약간 복잡

7-2. Re-ranking — 1차 검색 후 정밀 재정렬

1차 검색은 빠르지만 정확도가 100%는 아닙니다. top-20을 빠르게 가져온 뒤, 더 정밀한 모델(Cross-encoder)로 재정렬해 top-5만 LLM에 넘기는 방식이 흔합니다. Cross-encoder질문과 후보 문서를 한 신경망에 동시에 넣어 관련도를 직접 점수화하는 모델 — 1차 검색의 임베딩 모델(Bi-encoder)이 따로따로 인코딩하는 것과 대비됨. 정확도 ↑ 속도 ↓ trade-off는 질문과 chunk를 함께 보고 "이 chunk가 정말 답에 도움이 되는가"를 점수화합니다 (~10ms/chunk).

RE-RANKING 전후 비교

top-5 정확도가 어떻게 달라지나

[1차 검색만] top-5: ① ✓ ② ✓ ③ ✗ ④ ✓ ⑤ ✗ → 정확도 60% [1차 검색 + Re-ranking] top-20을 가져온 뒤 Cross-encoder로 점수 재계산 재정렬 결과 top-5: ① ✓ ② ✓ ⑥ ✓ ⑨ ✓ ④ ✓ → 정확도 100% → Re-ranking 추가만으로 정확도 60% → 100%, latency +200ms 추가

7-3. Multi-Query — 한 질문을 여러 변형으로

사용자가 묻는 방식은 한 가지지만, 비슷한 정보가 사내 문서에 여러 표현으로 흩어져 있습니다. LLM으로 질문을 3~5개 다른 표현으로 변형해 각각 검색한 뒤 결과를 합쳐주면 회수율(recall)이 크게 올라갑니다.

MULTI-QUERY 예시

한 질문 → 4가지 변형 검색

[원 질문] "OLED 도가니 교체 후 두께 변동 처리법" [LLM이 생성한 변형 질문] ① "도가니 교체 후 첫 lot 두께 spec 이탈 대응" ② "Crucible swap 직후 thickness drift 처리" ③ "증착 워밍업 단계 두께 변동 보정" ④ "OLED evaporator 도가니 교체 SOP" 각각으로 검색 → 결과를 union → 중복 제거 → 재정렬 → 단일 질문 대비 검색 회수율 1.5~2배 향상

7-4. Self-RAG — LLM이 스스로 검색 필요 여부를 판단

모든 질문이 RAG가 필요한 것은 아닙니다. "오늘 날씨는?" 같은 일반 질문은 검색이 무의미하고, "ECN-1129 사유는?"는 반드시 사내 문서를 봐야 합니다. Self-RAG는 LLM이 먼저 "이 질문에 사내 검색이 필요한가?"를 판단한 뒤, 필요할 때만 검색을 실행합니다. 불필요한 검색을 줄여 비용·latency를 절감합니다.

7-5. GraphRAG — 그래프 구조까지 활용

Microsoft가 2024년에 발표한 GraphRAG는 단순한 chunk 검색을 넘어 "엔티티 관계 그래프"를 미리 만들어 두는 방식입니다. "프로젝트 A의 담당자는 누구이고 그 담당자가 작성한 다른 보고서는?" 같은 관계 기반 질문에 강합니다. 구축 비용은 크지만(LLM으로 그래프 생성), 복잡한 사내 관계 탐색에 효과적입니다.

기법해결하는 문제구현 비용도입 우선순위
Hybrid Search식별자/이름 검색 약함낮음★★★ (필수)
Re-rankingtop-K 정확도 부족중간★★★ (강력 권장)
Multi-Query회수율 부족낮음★★ (도입 가치 큼)
Self-RAG불필요한 검색중간★ (선택)
GraphRAG관계 기반 질의높음★ (특수 use-case만)
실무 도입 순서: 기본 RAG → Hybrid Search → Re-ranking → (필요시) Multi-Query → (특수 use-case) Self-RAG / GraphRAG. 처음부터 모든 기법을 다 도입하지 마시고 단계적으로 추가하시는 것이 운영 관점에서 안전합니다.
8

사내 운영 관점 — 권한 · 평가 · 갱신

기술적 RAG는 만들기 어렵지 않습니다. 어려운 것은 "양산 운영을 1년 이상 안정적으로 유지"하는 것입니다. 그 핵심 3가지를 다룹니다.

8-1. 권한 관리 — "누가 어떤 문서를 볼 수 있나"

가장 큰 사고 시나리오: 사용자가 권한 없는 문서의 내용을 RAG로 받아보는 경우. 예: 개발 부서 신입이 "임원 회의록 요약해줘"라고 물었는데 RAG가 임원 회의록 chunk를 찾아 답변에 사용하는 사고. 이런 사고는 인덱스 단계에서 권한 메타데이터를 함께 저장하고 검색 시 필터링해야 막을 수 있습니다.

권한 관리 3계층

계층적용 시점구현 방법
① 문서 수집 시 인덱싱 단계 (Step 1-4) EDM 권한 정보를 chunk 메타데이터로 함께 저장 (department, security_level, project_id)
② 검색 시 Retrieval 단계 (Step 5) 사용자 권한과 chunk 메타데이터를 비교해 후보 사전 필터링
③ 답변 후 Audit log 모든 질의·검색·답변을 로그로 남겨 사후 감사 가능

8-2. 평가 메트릭 — "RAG가 정말 잘 작동하는가"

RAG는 두 단계의 평가가 필요합니다 — 검색의 품질과 답변의 품질은 별개입니다.

검색 품질 메트릭

메트릭정의좋은 값
Recall@Ktop-K 검색 결과에 정답 chunk가 포함된 비율≥ 0.85
MRR정답이 등장한 평균 순위의 역수 (Mean Reciprocal Rank)≥ 0.7
nDCG@K관련도 가중 순위 평가 (정밀)≥ 0.8

답변 품질 메트릭

메트릭정의측정 방법
Faithfulness답변이 검색된 문서를 충실히 따르는가LLM 또는 사람이 검토
Answer Relevance답변이 질문에 직접적으로 답하는가임베딩 유사도 또는 LLM 평가

8-3. 인덱스 갱신 — "최신 문서를 어떻게 반영하나"

문서는 매일 새로 만들어지고 수정됩니다. 인덱스를 갱신하지 않으면 RAG가 점점 stale해집니다. 갱신 전략 3가지:

전략주기장점단점
실시간 (Streaming) 문서 등록 즉시 최신 문서 즉시 반영 구현 복잡 · 인덱스 fragmentation
증분 (Incremental) 매일 야간 운영 단순 · 자원 효율 당일 신규 문서는 다음날 반영
전체 재구축 매월 1회 fragmentation 해소 · 모델 변경 시 필수 장시간 작업 (수 GB ~ TB)
실무 권장: 일반적으로 "매일 야간 증분 + 매월 전체 재구축"의 하이브리드가 가장 안정적입니다. 특별히 긴급한 ECN · 경고 문서만 실시간 인덱싱 채널을 별도로 둡니다.

8-4. 비용 관리 — "한 질문에 얼마가 드는가"

RAG 운영 비용은 크게 (1) 임베딩 생성 비용 (인덱싱 시 한 번) + (2) 매 질의 시 검색 + LLM 호출 비용으로 나뉩니다.

비용 분해 예시 (가상 시나리오)

사내 RAG 한 질문 비용 추정

[전제] - 사내 문서 50만 건, 600만 chunk, 평균 query 200/일 - LLM: GPT-4o (입력 $2.50/1M token, 출력 $10/1M token, 2024.08 기준) - 임베딩: text-embedding-3-small ($0.02/1M token) [인덱싱 (1회성)] 600만 chunk × 평균 400 token = 24억 토큰 임베딩 비용: 24억 × $0.02/1M = $48 저장 비용 (월): 24 GB × $0.02/GB = $0.48/월 [질의 1건당] 질문 임베딩: 50 token × $0.02/1M = $0.000001 (무시) 검색: 벡터 DB 자체 비용 (보통 시간당 $0.5~2) LLM 입력: 5 chunk × 400 token + 질문/시스템 ≈ 2500 token → 2500 × $2.50/1M = $0.00625 LLM 출력: 답변 200 token × $10/1M = $0.002 한 질문 총 비용 ≈ $0.008 (약 11원) [월간 비용 (가상)] 질의 200/일 × 30일 × $0.008 = $48/월 (약 6만 5천원) + 인프라 (벡터 DB · 모델 호스팅) ~수백 ~수천 USD/월

※ 위 수치는 가상 시나리오 기반 추정치입니다. 실제 비용은 모델 · 트래픽 · 인프라에 따라 크게 달라집니다.

INDUSTRY · 비용 절감 5가지 기법
  • ① 작은 LLM 우선: GPT-4o 대신 GPT-4o-mini · Llama 3.1 8B 자체 호스팅 (비용 1/10)
  • ② 캐싱: 같은 질문이 반복되면 캐시 히트로 LLM 호출 생략
  • ③ Self-RAG: 검색 불필요한 질문은 RAG 생략
  • ④ 양자화: 8B 모델을 4-bit로 양자화 → 메모리 1/4, 속도 2배
  • ⑤ 임베딩 차원 축소: 3072 → 1024로 줄여도 정확도 거의 유지 (저장·검색 비용 1/3)

FINAL TAKEAWAY

LLM · 벡터 · RAG의 본질

LLM은 "다음 토큰을 확률로 예측하는 함수"이고, 벡터(임베딩)은 "의미를 N차원 숫자로 표현한 것"이며, RAG는 "관련 문서를 찾아 LLM에 같이 보여주는 방법"입니다. Samsung Display 사내에서 IBM Watson + EDM 통합 LLM을 운영하실 때, 이 세 개념이 모든 작동의 기반이 됩니다.

개념한 줄 정의실무 의미
토큰LLM이 처리하는 텍스트의 최소 단위API 비용의 단위 · 한국어는 영어보다 1.5~3배 많음
임베딩의미를 N차원 숫자 벡터로 표현의미 검색의 기반 · 차원 768~1024 권장
코사인 유사도두 벡터의 방향 유사도 (-1~+1)0.7+ 유사 · 0.3 이하 무관
LLM다음 토큰을 확률 예측하는 함수autoregressive 생성 · 매개변수가 많을수록 미세
RAG검색 + 증강 + 생성환각 방지 · 최신 정보 · 사내 데이터 활용
벡터 DB벡터를 빠르게 검색하는 시스템HNSW · IVF로 100만에서 50ms 이내 검색
Hybrid Search키워드 + 시맨틱 검색 결합식별자 검색 약점 보완 (필수)

  • 임베딩: EDM에 등록된 PDF/PPT/Excel을 chunk로 분할 후 다국어 임베딩 모델로 벡터 변환

  • 오케스트레이터: 여러 인덱스(프로젝트별)를 묶어 사용자 질문에 맞게 라우팅
  • 운영: 매일 EDM 신규 문서 증분 인덱싱 · 매월 전체 재구축 · audit log · 평가 메트릭 모니터링
